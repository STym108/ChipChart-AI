# ChipChart AI - Frontend Logical Architecture Study Guide 🧠

This document is a deep-dive into the logical architecture of the ChipChart AI frontend. It is designed to serve as high-yield study material for your placement interviews. We will focus purely on *how* things work under the hood, the state management, the API integrations, and the algorithms used, rather than the CSS/styling.

---

## 1. Core Tech Stack (The "Why")

Before diving into the code, you must understand the stack choices. If an interviewer asks why you chose these technologies, here are your answers:
* **React 18 (Vite)**: Fast build times and standard component-based architecture.
* **Zustand**: Chosen over Redux because it is boilerplate-free, hook-based, and has built-in `localStorage` persistence middleware. Perfect for a multi-step form and a comparison cart.
* **TanStack React Query**: Used for data fetching. It handles loading states, error states, and query invalidation automatically.
* **React Router Dom v6**: Handles client-side routing (`/questionnaire`, `/results/pc`, etc.).

## 2. Global State Management (Zustand)

The frontend relies heavily on two global stores located in `src/store`.

### A. The Questionnaire Wizard (`questionnaireStore.ts`)
This store manages the complex multi-step form where users input their preferences.
* **How it works logically**: It tracks `currentStep` (integer) and an `answers` object. 
* **Key Functions**:
  * `setAnswer(key, value)`: Updates specific fields (e.g., `budget: 100000`).
  * `nextStep() / prevStep()`: Increments or decrements the step counter.
* **Persistence (`persist` middleware)**: Notice how the store uses `createJSONStorage(() => localStorage)`. This means if a user accidentally refreshes the page on step 5, their answers are instantly restored from `localStorage`. 

### B. The Comparison Basket (`bucketStore.ts`)
This acts like an e-commerce "Add to Cart" feature, but for comparing PC parts and laptops.
* **Duplicate Handling**: Inside the `addItem` function, there is logic to check if an item with the same name already exists. If it does, it simply increments the `quantity` instead of adding a duplicate row.

## 3. The Great Architecture Flow: How the Modules Communicate

If an interviewer asks, *"How does the data flow from the user's click to the final results screen?"*, this is your answer. These three modules—`geminiApi`, `livePricingApi`, and `recommendationEngine`—work in a highly coordinated relay race.

### Phase 1: The AI Generation (`geminiApi.ts`)
1. **The Trigger**: The user finishes the questionnaire and clicks submit. The `QuestionnaireAnswers` object (containing budget, purpose, resolution) is passed into `fetchGeminiPCBuilds()`.
2. **The Request**: `geminiApi.ts` does **not** call Google Gemini directly. Instead, it sends a `POST` request to your backend at `http://localhost:5001/api/recommend/pc`.
3. **The Response**: The backend securely talks to Gemini, gets the AI's recommendations, and returns a JSON array of `PCBuild` objects to the frontend. At this stage, the PC components only have "estimated" prices generated by the AI (which are often wrong or outdated).

### Phase 2: The Real-World Bridge (`livePricingApi.ts`)
1. **The Trigger**: Now that the frontend has the AI's list of components (e.g., "Intel i5-12400F", "RTX 4060"), it needs real prices.
2. **The Request**: The frontend maps over the components and calls `fetchLivePriceFromBackend(searchQuery)`. This function sends the specific component name back to the backend.
3. **The Response**: The backend uses ScraperAPI to secretly scrape Amazon India, parses the HTML, finds the actual live price, checks if it's in stock, and returns a `LivePriceResult` JSON object (`{ store: 'Amazon', price: 25000, inStock: true, url: '...' }`).
4. **The Merge**: The frontend receives this live price and **overwrites** the AI's estimated price with the actual real-world price.

### Phase 3: The Analytics & Insights (`recommendationEngine.ts`)
1. **The Trigger**: Now we have the final, fully-priced `PCBuild` array. We pass this massive array into `generatePCInsights(builds, answers)`.
2. **The Logic**: This engine acts like a data analyst. It loops through all the builds to find mathematical "Winners".
   * It calculates the **Best Overall** by finding the build with the highest `performanceScore`.
   * It calculates the **Best Value Pick** by finding the build with the highest ratio of `(performanceScore / totalPrice)`.
   * It calculates **Budget Fit** by taking the cheapest build and doing `savings = answers.budget - cheapest.totalPrice`.
3. **The Output**: It returns an array of `AnalysisInsight` objects. The React components (`LaptopResults.tsx` / `PCResults.tsx`) take these insights and render the beautiful "🏆 Best Overall" or "⚠️ Bottleneck Alert" badges on the screen.

## 4. Intelligent Caching System (`src/lib/apiCache.ts`)

LLM APIs and web scrapers are slow and cost money. To prevent the frontend from constantly begging the backend for the same data, we use a deeply logical caching system. This is a very senior-level implementation.

### A. Deterministic Cache Key Generation (The Sorting Trick)
How do you know if a user has asked for the exact same PC build before? You stringify their answers into a string and use it as a key in `localStorage`. 
* **The Problem**: In JavaScript, `{ budget: 50000, purpose: 'gaming' }` and `{ purpose: 'gaming', budget: 50000 }` are physically the same, but `JSON.stringify()` will output two completely different strings depending on the order of the keys! This would cause a cache miss.
* **The Solution**: Inside `apiCache.get()` and `apiCache.set()`, there is a `.sort().reduce()` chain. It alphabetically sorts all the keys in the object before stringifying it. This guarantees that no matter what order Zustand saved the data, the cache key will always perfectly match.

### B. Time-to-Live (TTL) Expiration
When data is saved to `localStorage`, we don't just save the JSON. We wrap it in an object with a timestamp: `JSON.stringify({ data, timestamp: Date.now() })`.
When `apiCache.get()` is called, it checks: `if (Date.now() - timestamp < 259200000)`. 
* `259200000` milliseconds is exactly 3 days. If the data is older than 3 days, the `if` statement fails, the stale cache is deleted via `localStorage.removeItem()`, and the frontend is forced to ask the backend for fresh data. (For live prices, the TTL is 1 day: `86400000` ms).

### C. Graceful Degradation & LRU Eviction (`safeSetItem`)
Browsers strictly limit `localStorage` to about 5MB. If the user searches for dozens of PCs, the storage will fill up, and the browser will throw a fatal `QuotaExceededError`, breaking the app.
* **The Solution**: The custom `safeSetItem` function wraps the `localStorage.setItem()` in a `try...catch` block.
* **The Eviction Logic**: If it catches an error, it doesn't crash. Instead, it grabs all keys starting with `gemini_cache_` or `pc_cache_`, sorts them, and slices the array in half: `keys.sort().slice(0, Math.ceil(keys.length / 2))`. It then loops through and deletes the oldest 50% of the cache entries, freeing up space, and retries saving the new data. This is a manual implementation of an LRU (Least Recently Used) cache strategy!

## 5. Summary for Interviews

If an interviewer asks you to explain the data flow and logic of your application, you can say:

> "The frontend uses a Zustand state machine to capture user requirements. When submitted, the data enters a three-phase pipeline. First, `geminiApi.ts` proxies the request through my backend to securely fetch AI-estimated PC builds. Second, `livePricingApi.ts` bridges the gap to reality by pinging the backend scraper to fetch real-time Amazon pricing for those specific components. Finally, the data flows into `recommendationEngine.ts`, which mathematically analyzes the builds to calculate value-to-cost ratios and identify bottlenecks. To ensure speed and save API costs, this entire process is backed by a custom deterministic `apiCache` that implements alphabetical key sorting and an LRU-style eviction policy when browser storage limits are hit."
